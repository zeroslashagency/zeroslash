# Living roots behind the ZeroSlash hero

Port the Sylva "living world" Three.js scene — the two tree roots, their moss and flowers, the pollen, the butterfly, the pointer reaction and the growth intro — into a React component that renders as the background layer of the existing homepage hero. Every moving part of the scene comes across. The hero keeps everything it has today: cream plate, black Playfair headline, bouquet, social bar, arrows, dots.

What gets dropped is the reference page's **content**, not its life: the nav dock, headline, lede, liquid-metal buttons, the stat readouts, the photo cards and their little data labels, the ghost wordmark, column guides and scroll cue. This site already has its own content, and those small pop-up plates and data blocks are exactly what you do not want repeated.

<Callout id="scope-line" tone="decision">

**The dividing line: every animated element ships, every informational element is cut.**

Ships: both roots, the moss fur, ferns, flowers, pollen drift, wind, the butterfly and its flight, the pointer bend and pointer-trail spray, the growth intro.

Cut: dock, headline, lede, buttons, stat rows ("Canopy restored 282 ha", "Native species 43 mapped"), the two photo cards with their "Our Ethos" / "Field Note 07" labels, ghost wordmark, guides, scroll cue.

</Callout>

<Callout id="scope-callout" tone="decision">

**Two facts from the codebase changed the approach the source skill describes.**

The skill says to copy the HTML byte-for-byte into `public/` and load it in an iframe. That cannot work here: `next.config.mjs` sends `X-Frame-Options: DENY` and `frame-ancestors 'none'` on `/(.*)` (lines 34, 58), and those headers apply to the framed document too, so a same-origin iframe of that page is blocked by the site's own security policy.

The scene does not need the iframe. Its script uses **core Three.js only** — no `three/examples` addons, no `EffectComposer`, no `OrbitControls`. So it ports cleanly to a real React component against the `three` npm package, which is also the only way the scene can share the hero's cream plate instead of covering it with its own dark page.

</Callout>

Every material is a hand-written `ShaderMaterial` with a shared GLSL light rig — there are **zero `THREE.Light` objects** in the scene. All lighting, haze, and the growth-reveal gate live in GLSL. That matters for the retone: changing how the roots read on cream means editing uniform colours in the light rig, not adding lights.

The pointer interaction is real 3D, not a CSS parallax trick: a raycast hits a plane at the root's crown, the hit is converted into each root group's local space, smoothed per-frame, and fed to the grass shader as `uMouse` so blades bend away from the cursor.

## The one thing that makes the placement port cleanly

The scene's root placement is driven entirely off a `#stage` element measured against a 1600 × 880 reference frame. The camera is a `PerspectiveCamera` whose field of view is re-solved on every layout so that **one world unit equals one CSS pixel at z = 0**:

So the port does not need to redesign the layout. It substitutes a **synthetic stage** — a computed box rather than a measured element — and every downstream number (root scale, shadow and glow planes, scan origin, point-size attenuation) keeps working untouched.

**One thing has to be un-wired for this to work.** In the source the butterfly is only built when the scene is *not* in its cheap tier — line 3424 reads `if (!small) buildButterfly(...)`, and `small` is the same flag that cuts the blade counts. ## Two butterflies, and a frozen frame on phones

Both of these need a little more than a changed number, so they are worth being explicit about.

### The second butterfly needs its own state, not a second copy

The source builds exactly one butterfly and keeps its flight state in variables captured by the module closure — perch target, phase, timers, the spooked response to `uMouseNear`. Calling the builder twice would produce two meshes sharing one set of state variables, and they would fly in perfect lockstep.

So the flight state moves into an object the builder returns, one per butterfly, and the frame loop ticks each in turn. Offsetting them is then just seeding different values.

<AnnotatedCode
  id="butterfly-instances"

## Retoning the roots for a cream plate

The reference scene is lit for a `#4a4d44` page: dark green ambient, dark green distance haze, and a warm key that reads as sunlight in a shaded grove. Dropped straight onto cream, the roots would read as a heavy dark silhouette fighting your black Playfair headline.

Because the renderer is already created with `alpha: true` and `setClearColor(0x000000, 0)`, the cream comes through from the CSS behind the canvas with no change at all. The work is in four uniform colours in the shared light rig:

### Host lifecycle

This is the genuinely new code. It follows the convention already used by the gap-slider in `app/page.tsx` (lines 64–99): bail to a static state on reduced motion, gate the loop on an `IntersectionObserver`, cancel and disconnect on unmount.

<Code
  id="host-shape"
  filename="components/hero/sylva-roots/SylvaRootsBackground.tsx"
  language="tsx"
  caption="Everything the source leaks, cleaned up on unmount."
  code={"\"use client\"\n\nimport { useEffect, useRef, useState } from \"react\"\n\nexport default function SylvaRootsBackground() {\n  const canvasRef = useRef<HTMLCanvasElement>(null)\n  const hostRef = useRef<HTMLDivElement>(null)\n  const [ready, setReady] = useState(false)\n\n  useEffect(() => {\n    const canvas = canvasRef.current\n    const host = hostRef.current\n    if (!canvas || !host) return\n\n    let disposed = false\n    let scene: { dispose: () => void; setActive: (on: boolean) => void } | null = null\n\n    // Dynamic import keeps three out of the initial homepage bundle.\n    import(\"./scene\").then(({ createScene }) => {\n      if (disposed) return\n      scene = createScene({ canvas, container: host, onReady: () => setReady(true) })\n    })\n\n    const io = new IntersectionObserver(\n      ([entry]) => scene?.setActive(entry.isIntersecting),\n      { rootMargin: \"120px\" },\n    )\n    io.observe(host)\n\n    const onVisibility = () => scene?.setActive(!document.hidden)\n    document.addEventListener(\"visibilitychange\", onVisibility)\n\n    return () => {\n      disposed = true\n      io.disconnect()\n      document.removeEventListener(\"visibilitychange\", onVisibility)\n      scene?.dispose()\n    }\n  }, [])\n\n  return (\n    <div\n      ref={hostRef}\n      aria-hidden\n      className=\"pointer-events-none absolute inset-0 z-0\"\n      style={{ opacity: ready ? 1 : 0, transition: \"opacity .7s cubic-bezier(.22,.61,.36,1)\" }}\n    >\n      <canvas ref={canvasRef} className=\"h-full w-full\" />\n    </div>\n  )\n}\n"}
/>

`dispose()` inside `scene.ts` has to cancel the frame loop, remove the pointer and resize listeners, clear both boot `setTimeout`s, guard the `document.fonts.ready` callback, traverse the scene disposing geometries and materials, dispose the canvas textures, then `renderer.dispose()` and `renderer.forceContextLoss()`. The source does none of this, so it is written fresh — and it is what makes the hero survive React fast-refresh and route changes without leaking a WebGL context.

<Callout id="pointer-events" tone="info">

The host is `pointer-events: none` so it never steals clicks from the Start-a-project button, arrows, or social links. The scene reads the cursor from a `window`-level `pointermove` listener and converts it to normalized device coordinates itself, so the pointer interaction still works with the layer inert.

</Callout>
